# 深度研究系统 AI 应用开发扩展计划

## 1. 文档目的

本文档用于规划 LangGraph Deep Research 项目的后续扩展，目标是将当前的多 Agent 研究原型进一步完善为一个具备以下能力的 AI 应用：

- 输出可控：模型输出经过结构化解析和规则校验；
- 过程可观测：能够查看任务状态、工具调用、重试和失败原因；
- 结果可追溯：报告结论能够关联到真实检索来源；
- 质量可评估：Prompt、模型和流程调整能够通过离线数据集回归验证；
- 交互可控：用户可以确认或修改研究计划后再执行；
- 成本可控：能够限制任务数量、重试次数、Token 和外部搜索调用。

这些能力优先服务于 AI 应用开发、AI Agent 和 AI 平台岗位的项目展示。

### 范围与非目标

本计划以“可完整演示、可重复验收的个人项目”为范围，不以生产级多租户、高并发或完全自动事实判定为目标。

- 不将可访问 URL 视为“结论已被事实证明”；
- 不承诺对任意模型输出都能无条件修复；
- 不把 LangSmith Trace 当作用户侧实时交互能力的替代；
- 不在未完成持久化设计前宣称支持生产级断点续跑；
- 用户文档能力仅在完成访问隔离、删除索引和文件安全控制后再扩展。

## 2. 当前能力基线

当前系统已经实现：

1. 使用 LangGraph 编排 `Planner -> 并行 Summarizer -> Reporter` 研究流程；
2. 使用 `Send` 分发多个研究任务，并通过列表聚合并行结果；
3. Summarizer 支持网页搜索、学术论文搜索和本地笔记工具；
4. 网页搜索具备 Tavily、DuckDuckGo、Wikipedia 多级降级路径；
5. 研究任务具备有限重试、替代查询和无结果降级；
6. 使用短期会话记忆和 ChromaDB 长期语义记忆；
7. 提供 FastAPI 接口、SSE 接口、Vue 前端、多轮会话和历史记录；
8. 已有 Planner、Summarizer、Reporter 分层评测代码。

核心实现位置：

| 能力 | 代码位置 |
| --- | --- |
| LangGraph 研究流程 | `src/graph/research.py` |
| 状态和来源模型 | `src/state.py` |
| Planner/Summarizer/Reporter | `src/agents/` |
| 搜索与论文工具 | `src/tools/search.py` |
| 短期、长期记忆 | `src/memory/` |
| FastAPI 与会话 | `src/main.py`、`src/session.py` |
| 离线评测 | `src/evaluation/` |

## 3. 现状问题与事实边界

### 3.1 评测数据需要统一

当前仓库中的评测文件 `evaluation_results_new.json` 显示：

- 评测主题数：12；
- 整体平均分：72.3；
- Planner 平均分：94.2；
- Summarizer 平均分：61.1；
- Reporter 平均分：96.7。

旧文档中出现的“15 个课题、平均 94.6/100”等数据与当前评测文件不一致。在重新运行评测并保存新的结果前，不应在简历或面试中使用旧指标。

### 3.2 当前能力不能过度表述

以下内容目前不能直接视为已完成能力：

- 报告中每个结论与来源之间的严格引用映射；
- 用户确认研究计划后再执行的完整人机协同流程；
- 跨进程、可恢复的持久化会话；
- 生产级的 Token、成本和延迟监控；
- 完整的自动化测试和持续集成回归；
- 由 LangGraph 统一编排的意图路由流程。

### 3.3 设计原则

后续扩展遵循以下原则：

1. **先定义数据契约，再增加 Agent 能力**：跨节点传递的数据必须具备稳定 ID、版本和可序列化结构；
2. **失败显式化**：解析失败、来源不足、预算超限和外部工具失败均应进入可查询状态，而不是用看似正常的文本掩盖；
3. **评测可复现优先于单次高分**：同一输入、模型、Prompt、工具版本和来源快照应能重复比较；
4. **观测默认最小化**：Trace 和日志只记录诊断必需信息，内容采集必须满足脱敏和环境策略；
5. **简历指标可追溯**：所有数字都要能对应原始评测结果、运行记录或验收脚本。

## 4. 扩展优先级

建议按照“可靠性 -> 可评估性 -> 交互控制 -> 工程化”的顺序实施。

### P0：结构化输出与自动修复

#### 目标

减少 Planner 任务解析失败、字段缺失、来源格式错误和 Agent 间数据传递不稳定的问题。

#### 计划

1. 在 `src/state.py` 中定义版本化、可序列化的研究产物：
   - `ResearchRun`：`run_id`、`thread_id`、`plan_id`、`plan_version`、模型版本、Prompt 版本和运行状态；
   - `TaskPlan`：研究主题、任务列表和计划版本；
   - `TaskItem`：`task_id`、任务标题、意图、查询、状态和查询修订历史；
   - `TaskResult`：`task_id`、状态、尝试次数、摘要、`source_ids`、错误码、延迟和 Token 统计；
   - `SourceItem`：`source_id`、规范化 URL、来源类型、抓取时间、内容哈希、证据片段和定位信息；
   - `TaskSourceRef`：`task_id`、`source_id`、检索查询、尝试次数和关联时间；
   - `Claim`：报告结论文本、`claim_id` 和支撑该结论的 `source_ids`。
2. LangGraph State 保持 JSON 可序列化；Pydantic 只用于节点输入输出边界校验，避免 checkpoint 因对象序列化失败；
3. 并行节点按 `task_id` 写入结果；来源实体按 `source_id` 去重，任务与来源通过 `TaskSourceRef` 关联；Reporter 按计划中的 `task_id` 顺序汇总，不能依赖并行列表的返回顺序；
4. 使用 Pydantic 对 Planner 和 Summarizer 输出进行校验，并保留原始响应摘要和失败原因用于诊断；
5. 对模型输出增加有限次数的修复重试；超过上限时返回 `rejected` 状态和可读错误，不继续执行不合法计划；
6. 对任务数量、重复查询、空字段、非法 URL 和超长内容增加规则校验；
7. 将解析状态区分为 `valid`、`repaired`、`rejected`，记录修复次数和最终状态。

#### 验收标准

- 合法输出转换为 `TaskPlan`，不合法输出在有限修复后进入明确的 `rejected` 状态；
- 任务数量、必填字段、重复查询和 State 序列化均有自动校验；
- 并行任务结果与 `task_id` 一一对应，Reporter 汇总顺序可重复；
- 解析失败不会导致服务异常退出或执行未校验任务；
- 至少覆盖合法 JSON、Markdown 包裹 JSON、字段缺失、非法 JSON、重复任务、并行结果乱序和 checkpoint 序列化七类测试样例。

#### 简历价值

体现 LLM 输出约束、数据契约、错误修复和 Agent 系统可靠性，而不是只体现 Prompt 调用。

### P0：来源追踪与引用校验

#### 目标

建立“检索结果 -> 任务摘要 -> 报告结论”的可追溯链路，降低无依据生成风险。

#### 计划

1. 搜索工具先将结果转换为标准 `SourceItem`，在工具返回 JSON 中暴露稳定 `source_id`，保存规范化 URL、来源类型、抓取时间、内容哈希、摘要片段和原文定位信息；
2. 图层根据当前 `task_id` 创建 `TaskSourceRef`，对不同搜索引擎返回的来源实体按规范化 URL 和内容哈希去重，并在关联记录中保留来源引擎、查询和抓取时间；
3. Summarizer 输出 `TaskResult` 与 `Claim`，每个关键结论引用本任务的 `source_id`，而不是仅在末尾输出 URL JSON；
4. Reporter 按 `claim_id -> source_ids` 生成报告引用，并保留“证据不足”状态；
5. 增加引用校验器，将引用质量拆分为：
   - **结构有效**：`source_id` 存在，且当前任务存在对应的 `TaskSourceRef`；
   - **可访问**：URL 或保存的快照可读取；
   - **证据支持**：引用的片段与结论存在可说明的支撑关系。
6. “证据支持”先针对固定评测集的关键结论做人工标注；后续可引入经人工抽样校准的 LLM Judge，不能只依赖 URL 连通性；
7. 统计来源存在率、来源可访问率、结构化引用覆盖率、人工/LLM Judge 的证据支持率和证据不足结论比例。

#### 验收标准

- 每个 `TaskResult` 与 `source_ids` 及其证据片段能够关联；
- 报告中的不存在引用、跨任务引用和重复引用可以被自动识别；
- 评测结果中严格区分来源存在、来源可访问、引用结构有效和证据支持四种情况；
- 固定评测集中的关键结论具备人工标注或经校准 LLM Judge 的证据支持判定；
- 搜索失败或来源不足时，报告明确标注证据不足，而不是生成无法验证的结论。

#### 简历价值

体现检索增强、事实依据、引用追踪和降低幻觉的工程实践。仅在用户文档检索链路完成后，将该能力表述为完整 RAG。

### P0：离线评测与回归体系

#### 目标

让模型、Prompt、搜索工具和工作流调整可以被量化比较，避免只凭主观体验判断效果。

#### 计划

1. 建立版本化评测清单，每条用例包含 `case_id`、研究主题、预期覆盖维度、关键结论、允许来源范围和来源快照引用；覆盖技术综述、论文调研、事实问答和对比分析；
2. 对公开网页和论文检索保存评测所需的最小证据快照（URL、抓取时间、摘要片段、内容哈希），避免实时搜索变化破坏横向比较；
3. 修正 `EvaluationRunner`，确保 Planner 评测结果和完整研究流程使用一致的任务输入；
4. 即使来源为空，也要输出 Reporter 评测结果，避免结果缺失造成统计偏差；
5. 保留当前启发式指标，同时增加：
   - 任务字段完整率；
   - 基于预期维度标注的任务覆盖率和重复率；
   - 来源存在率、来源可访问率；
   - 结构化引用覆盖率和证据支持率；
   - 报告章节完整率；
   - 平均延迟、失败率、重试率和 Token 消耗。
6. 为每次评测记录模型、Prompt、工具、数据集、来源快照、评测器和代码版本；
7. 对每个配置至少运行 3 次，报告中位数、最小值、最大值和失败率，避免将单次结果作为结论；
8. 输出可比较的 JSON 结果和 Markdown 报告，并保存到不可覆盖的按时间和版本命名目录。

#### 验收标准

- 固定主题集与对应来源快照可以一键批量执行；
- 同一模型、Prompt、工具和快照条件下的多次运行可比较，并能报告波动范围；
- 任务覆盖率和证据支持率都有明确的标注规则；
- 评测结果包含成功、失败和降级任务，而不是只统计成功样本；
- 评测文档中的数字、版本号与 JSON 原始结果保持一致。

#### 简历价值

体现 AI 应用的离线评测、回归分析和模型工程能力。完成后可以使用真实的平均分、引用覆盖率和失败率，但必须以实际结果为准。

### P1：研究计划确认与可恢复执行

#### 目标

将当前的 `/plan` 接口扩展为真正的人机协同流程。

#### 计划

```text
用户输入主题
    -> Planner 生成任务计划
    -> 用户确认、删除或修改任务
    -> 执行已确认计划
    -> 并行检索与摘要
    -> Reporter 生成报告
```

1. 为研究任务生成 `run_id`、`plan_id`、`plan_version` 和 LangGraph `thread_id`；
2. 增加计划查看、修改、确认和取消接口，计划修改后创建新的 `plan_version`，已确认计划不可原地覆盖；
3. 执行接口只接受已确认的计划，并校验 `plan_id + plan_version`，避免执行过期计划；
4. 个人项目阶段选择持久化 checkpointer（优先 SQLite），将 `ResearchRun`、任务状态和 checkpoint 分开保存；生产级数据库替换不属于本阶段范围；
5. 所有 State 字段保持 JSON 可序列化并带 `schema_version`，支持后续状态迁移；
6. 支持单个任务失败后重新执行，不重复成功任务；Reporter 根据当前版本的 `TaskResult` 重建报告并记录 `report_version`；
7. 明确任务状态机：`planned -> confirmed -> running -> succeeded | failed | cancelled`，重试不改变任务 ID；
8. 前端展示计划版本、任务状态和执行进度。

#### 验收标准

- 用户可以在执行前修改任务；
- 计划确认后才触发搜索和模型调用；
- 服务进程重启后，能够使用同一 `thread_id` 从最近 checkpoint 恢复；
- 单个任务重试不会重复执行已成功任务，并生成新的报告版本；
- 过期 `plan_version`、状态不合法和 State 反序列化失败都有明确错误；
- 使用 mock 工具覆盖确认、取消、中断恢复和单任务重试四类集成测试。

#### 简历价值

体现 AI Agent 的可控执行、人机协同、状态持久化和工作流恢复能力。

### P1：任务级状态与可观测性（LangSmith + 本地事件流）

#### 目标

将当前的字符串日志和粗粒度 SSE 输出升级为可用于诊断的 Agent 运行记录，并接入 LangSmith 观察 LangGraph、LLM 和工具调用的完整链路。

LangSmith 与本地事件流承担不同职责：

- **LangSmith**：保存开发调试和评测所需的 Trace，查看节点嵌套关系、Prompt、模型响应、工具调用、耗时和异常；
- **本地结构化事件流**：服务端向前端推送任务进度，支持用户体验、业务状态和失败提示；
- **本地运行摘要**：保存脱敏后的运行指标，便于没有网络或没有 LangSmith 权限时继续诊断。

#### 计划

##### LangSmith 接入

1. 增加可选的 LangSmith 配置，不把 API Key 写入代码：
   - `LANGSMITH_TRACING`；
   - `LANGSMITH_API_KEY`；
   - `LANGSMITH_PROJECT`；
   - `LANGSMITH_ENDPOINT`（按部署环境配置）。
2. 默认策略：本地开发和评测环境可显式开启 Trace；部署环境默认关闭内容采集，只有在完成脱敏和采样配置后才开启；
3. 为一次研究生成稳定的 `research_id`，并将以下最小必要信息作为 LangSmith tags 或 metadata：
   - `research_id`；
   - `session_id`；
   - `task_id`；
   - Agent 节点名称；
   - 模型名称和 Prompt 版本；
   - 搜索源和重试次数。
4. 默认不上传 API Key、认证头、完整用户文档、完整研究报告和原始搜索内容；需要内容级诊断时先执行脱敏，并设置采样率和保留期限；
5. 为 Trace 定义删除与访问策略：项目隔离、最小访问权限、保留期限和按 `research_id` 删除能力；
6. 确保 LangGraph 的父级运行能够关联 Planner、Summarizer、Reporter 和工具子调用；
7. LangSmith 不可用时，研究流程仍然能够运行，并保留本地错误日志和脱敏后的运行摘要。

##### 本地任务状态与事件

每个任务记录：

```text
task_id
status
attempts
query
sources
summary
error
latency_ms
token_usage
```

SSE 事件统一为：

```text
planning
task_started
searching
retrying
task_completed
task_failed
reporting
completed
```

同时记录：

- Agent 节点耗时；
- 工具调用次数和失败原因；
- 外部搜索源；
- 模型调用次数、Token 和估算成本；
- 每个任务的重试和降级原因。

#### 验收标准

- 前端可以实时展示每个任务的状态；
- 一次失败可以定位到具体 Agent、工具和查询；
- 运行结束后可以导出完整 trace；
- 在 LangSmith 中可以从一次研究运行展开到具体 Agent 节点和工具调用；
- 可以根据 `research_id`、`session_id`、`task_id` 和模型版本筛选运行记录；
- 关闭 LangSmith 或网络不可用时不影响核心研究流程；
- Trace 和本地运行记录不包含 API Key、认证头及未经脱敏的用户私有内容；
- Trace 的采样率、保留期限、内容采集开关和删除流程均有配置与验收记录。

#### 简历价值

体现 AI 应用上线所需的可观测性、LangGraph 链路追踪、故障诊断和用户体验工程。

### P1：模型路由、缓存与成本控制

#### 目标

在保证效果的同时降低研究流程的平均调用成本和等待时间。

#### 计划

1. Router、Planner 和简单追问使用轻量模型；
2. Summarizer、Reporter 使用能力更强的模型；
3. 对外部搜索结果增加带 TTL 的缓存，缓存键至少包含规范化查询、来源配置、语言、最大结果数和工具版本；
4. 为单次研究设置最大任务数、最大重试次数和 Token 预算；
5. 对搜索任务增加超时、并发上限和指数退避；
6. 缓存条目保留 `source_id`、来源快照和过期时间；命中缓存时在报告和 Trace 中标记，避免把旧来源伪装成实时结果；
7. 在评测中对比不同模型路由策略的质量、延迟和成本。

#### 验收标准

- 每次研究都能统计模型调用和搜索调用次数；
- 超出预算时能够提前停止或降级；
- 缓存命中不会破坏来源追踪；
- 相同缓存键的查询可复用，来源配置或工具版本变化会自动失效；
- 评测结果同时包含质量、延迟和成本指标。

#### 简历价值

体现 LLM 应用中的成本优化、性能控制和多模型协同。

### P2：用户文档和 PDF 研究

#### 目标

从公开网页研究扩展到用户上传资料的知识库研究，形成更完整的 RAG 应用场景。

#### 计划

1. 支持 Markdown、PDF 和网页内容导入；
2. 对上传文件执行类型白名单、大小限制、解析超时和安全文件名处理；
3. 对文档进行分块、元数据标记和向量化，记录文档 ID、版本、页码或段落定位；
4. 检索时区分用户资料和公开网页，并以文档范围作为访问边界；
5. 报告中标明来源类型、文档名称和页码；
6. 增加文档删除、重建索引、版本管理和删除后检索回归测试。

#### 验收标准

- 用户上传文档后能够在指定范围内检索；
- 报告可以区分内部资料和公开来源；
- 删除文档后不会继续返回其内容；
- 超出类型、大小和解析限制的文档被拒绝且有明确错误信息；
- 文档解析失败时有明确错误信息。

#### 简历价值

体现文档解析、RAG、知识库生命周期和企业知识问答能力。

## 5. 推荐实施组合

考虑项目规模和简历收益，不建议一次实现全部方向。推荐采用以下组合：

### 第一阶段：可靠性基础

- `P0.1`：定义 `ResearchRun`、`TaskPlan`、`TaskResult`、`SourceItem` 和 `Claim` 数据契约；
- `P0.2`：将并行任务结果按 `task_id` 归并，补齐结构化输出、有限修复和失败状态；
- `P0.3`：实现来源标准化、证据片段保存和引用结构校验；
- 对应单元测试和并行归并集成测试。

### 第二阶段：可评估性

- 建立含预期维度和来源快照的固定离线数据集；
- Planner/Summarizer/Reporter 一致性评测和关键结论证据支持标注；
- 对每个配置重复运行，统计质量波动、延迟、Token、成本和失败率；
- 接入 LangSmith 作为开发与评测 Trace，先完成内容脱敏和采样策略。

### 第三阶段：产品化交互

- 计划确认和修改，使用版本化 `plan_id + plan_version`；
- 任务级 SSE 状态和本地结构化事件；
- SQLite checkpoint 恢复、报告版本化和单任务重试；
- 模型路由、搜索缓存与预算控制。

完成前三阶段后，项目就可以从“多 Agent 搜索 Demo”定位为：

> 面向深度研究场景的可控、可评估、可追溯多 Agent AI 应用。

## 6. 简历表述建议

以下表述仅适用于对应功能已经实现并完成验证之后。

### 当前版本可使用

- 基于 LangGraph 构建 Planner、Summarizer、Reporter 多 Agent 研究流程，使用 `Send` 并行执行多个检索任务并聚合结果；
- 集成网页搜索、ArXiv、Semantic Scholar 和本地笔记工具，支持搜索失败重试、替代查询和多级降级；
- 使用短期会话记忆与 ChromaDB 长期向量记忆支持多轮追问和跨会话研究复用；
- 使用 FastAPI、Vue 3 构建研究服务及交互界面，提供 SSE 研究流接口，并实现 Planner、Summarizer、Reporter 分层离线评测；当前聊天主流程仍使用会话 REST 接口。

### 完成 P0 后可使用

- 使用 Pydantic 建立任务规划、摘要和来源的数据契约，增加结构化解析、输出校验和有限自动修复；
- 建立来源标准化和引用校验链路，将研究结论关联到可验证检索来源，量化来源有效率和引用覆盖率；
- 构建模型、Prompt、工具和评测数据集版本隔离的离线回归框架，支持 Agent 流程迭代后的质量对比。

### 完成 P1 后可使用

- 实现研究计划确认、任务级状态跟踪和 checkpoint 恢复，支持用户修改研究计划及单任务重试；
- 接入 LangSmith 追踪 LangGraph 节点、LLM 与工具调用，通过结构化事件流记录 Agent 节点、重试、延迟和 Token 消耗，并实时推送研究进度；
- 根据任务复杂度进行模型路由和成本预算控制，结合搜索缓存降低重复调用。

## 7. 面试中的事实边界

可以说：

- “我采用 LangGraph 管理有状态的多 Agent 研究流程。”
- “我针对搜索失败和模型输出不稳定设计了重试、降级和质量检查。”
- “我正在将启发式评测升级为可回归的离线评测体系。”

不能在功能完成前说：

- “每个结论都具备严格引用证明”；
- “支持生产级断点续跑”；
- “已经实现完整 Token 成本监控”；
- “评测平均分达到 94.6/100”；
- “系统具备生产级高并发能力”。

## 8. 完成定义

一个扩展只有在以下条件同时满足时，才建议写入简历：

1. 代码已经合并到当前项目；
2. 至少有对应的自动化测试或可重复验收脚本；
3. 能够在本地完整演示；
4. 关键指标有原始结果文件；
5. 能够解释设计取舍、失败场景和后续改进方向；
6. 涉及 Trace、用户文档或外部数据时，已完成对应的脱敏、访问边界和删除验收。
