# LangGraph DeepResearch — 面试项目介绍与问答

---

## 一、项目概述（1分钟电梯介绍）

> 这是一个基于 **LangGraph** 的深度研究助手系统，采用多智能体协作架构，能自动将复杂研究课题分解为多个子任务，并行执行网络搜索与摘要，最终生成结构化的研究报告。系统具备双层记忆机制（短期会话记忆 + 长期向量记忆）、意图路由、多源搜索降级策略，并提供 Vue 3 前端实现多轮对话式交互。

## 二、项目详细架构

### 2.1 技术栈

|------|------|------|

| 后端 | FastAPI | REST API + SSE流式推送 |
| 前端 | Vue 3 + Vite | 响应式对话界面 |
| 数据验证 | Pydantic 2.0 | 类型安全的配置管理 |

### 2.2 核心流程

```
用户输入 → 意图路由(Router)
    │
    ├─ new_research ──→ 完整研究流程
    ├─ follow_up ─────→ 基于历史报告的追问
    ├─ refine_tasks ──→ 任务调整
    └─ general ───────→ 普通对话
```

**完整研究流程：**

```
Planner Agent（任务分解）
    ↓ 生成 5~7 个互补子任务
    ↓
LangGraph Send（并行分发）
    ↓
┌──────────────────────────────────┐
│  Task 1 → Search + Summarize    │
│  Task 2 → Search + Summarize    │  ← 并行执行
│  Task 3 → Search + Summarize    │
│  ...                            │
└──────────────────────────────────┘
    ↓ 结果聚合（operator.add）
    ↓
Reporter Agent（报告生成）
    ↓ 结构化研究报告
    ↓
保存至长期记忆(ChromaDB) + 历史记录
```

### 2.3 四大核心Agent

| Agent | 职责 | 可用工具 | 输出 |
|-------|------|----------|------|
| **Planner** | 将复杂课题分解为5-7个互补研究任务 | `search_notes` | JSON任务列表 |
| **Summarizer** | 执行网络搜索并生成综合摘要 | `search_web`, `create_note`, `read_note`, `update_note` | 带引用的结构化摘要 |
| **Reporter** | 汇总所有摘要生成最终报告 | `create_note`, `read_note` | Markdown研究报告 |
| **Router** | 意图分类（新研究/追问/调整/闲聊） | 无 | 路由标签 |

### 2.4 双层记忆系统

```
┌─────────────────────────────────────────────────┐
│  短期记忆 (ConversationSummaryBufferMemory)      │
│  · 会话级别隔离                                  │
│  · max_token_limit=2000，超限自动摘要            │
│  · 用于多轮对话上下文                            │
├─────────────────────────────────────────────────┤
│  长期记忆 (ChromaDB VectorStore)                 │
│  · 持久化存储所有研究报告                        │
│  · 语义相似度检索 top-3 历史研究                 │
│  · 跨会话知识复用                                │
└─────────────────────────────────────────────────┘
```

### 2.5 三级搜索降级

```
Tavily API（主要） → DuckDuckGo（免费备用） → Wikipedia（兜底）
    ↓ 失败/配额耗尽          ↓ 失败              ↓ 最终保底
```

### 2.6 质量保障机制

- **任务规划**：JSON格式校验、字段完整性检查、任务多样性验证
- **搜索摘要**：最多3次重试、内容长度阈值(>200字符)、来源数量检查
- **报告生成**：6大章节完整性验证、Markdown格式校验、引用链接有效性

## 五、面试问答

### 第一类：项目架构与设计

#### Q1: 请介绍一下你这个项目是做什么的？

**A:** 这是一个基于LangGraph的深度研究助手。用户输入一个研究课题，系统会自动将它分解成5-7个互补的子任务，然后并行执行网络搜索和信息整合，最终生成一份包含背景概述、核心洞察、证据数据、风险挑战和参考文献的结构化研究报告。系统支持多轮对话，可以基于已有报告进行追问，也具备跨会话的知识记忆能力。

---

#### Q2: 为什么选择LangGraph而不是直接用LangChain的Chain？

**A:** 三个关键原因：
1. **并行执行**：研究任务天然适合并行处理，LangGraph的`Send`机制可以同时启动多个搜索摘要节点，结果通过`operator.add`注解自动聚合到状态中，这是普通Chain做不到的
2. **状态管理**：LangGraph的StateGraph提供了全局共享状态，所有节点可以读写同一个状态对象，避免了手动传递数据的复杂性
3. **条件路由**：意图分类后需要走不同的处理分支（新研究、追问、普通对话），LangGraph的条件边天然支持这种分支逻辑

---

#### Q3: 你的多Agent是怎么协作的？Agent之间如何通信？

**A:** 采用的是**共享状态 + 顺序/并行编排**的模式：
- **顺序协作**：Planner → Summarizer → Reporter，通过共享的`ResearchState`传递数据
- **并行协作**：多个Summarizer实例同时执行，每个实例拿到独立的task，但结果写入同一个`task_results`列表（通过`Annotated[list, operator.add]`实现自动合并）
- Agent之间不直接通信，而是通过状态对象间接传递信息。Planner的输出（任务列表）成为Summarizer的输入，Summarizer的汇总成为Reporter的输入

---

#### Q4: 为什么用双层记忆而不是单层？

**A:** 两层记忆解决的是不同的问题：
- **短期记忆**（ConversationSummaryBufferMemory）：解决单次会话内的上下文连贯性问题。用户可能在生成报告后追问细节，需要记住之前的对话内容。设置max_token_limit=2000，超出时自动摘要，平衡了上下文长度和成本
- **长期记忆**（ChromaDB向量库）：解决跨会话的知识积累问题。当用户研究新课题时，系统可以检索历史上相关的研究报告作为参考，避免重复搜索，也能发现跨领域的知识关联

如果只用短期记忆，每次新会话都从零开始；如果只用长期记忆，单次对话的上下文无法维持。

---

### 第二类：AI/LLM 技术细节

#### Q5: 什么是ReAct模式？你项目里是怎么用的？

**A:** ReAct（Reasoning + Acting）是一种让LLM交替进行推理和行动的Agent模式。每一轮循环中：
1. **Reasoning**：LLM分析当前状态，决定下一步做什么
2. **Acting**：LLM选择并调用一个工具（如search_web）
3. **Observation**：将工具返回结果反馈给LLM
4. **迭代**：LLM决定是否继续行动还是给出最终回答

在我的项目中，三个核心Agent都使用LangChain的`create_react_agent`构建。比如Summarizer Agent，它会先调用`search_web`获取信息，然后可能调用`create_note`保存笔记，再调用`read_note`回顾笔记内容，最后综合所有观察生成摘要。这种模式让Agent能够自主决策调用哪些工具、调用几次，而不是硬编码固定的调用链。

---

#### Q6: 你的搜索工具是怎么处理失败的？三级降级具体怎么实现？

**A:** 实现了一个逐级降级的策略：
```python
try:
    results = tavily_search(query)       # 第一选择：Tavily（结果质量高）
except QuotaExceededError:
    results = duckduckgo_search(query)   # 第二选择：DuckDuckGo（免费）
    if not results:
        results = wikipedia_search(query) # 第三选择：Wikipedia（兜底）
```

同时在Summarizer层面还有重试机制：
- 每个任务最多尝试3次
- 失败后会生成替代搜索查询重新搜索
- 检查内容长度是否>200字符、是否包含来源引用
- 如果3次都失败，生成一段基于LLM知识的回退内容，确保流程不会中断

---

#### Q7: Embedding模型和LLM为什么要分开配置？

**A:** 出于成本和性能的考虑：
- **LLM**（如GPT-4）：负责理解、推理和生成，需要强大的语言能力，调用成本高
- **Embedding模型**（如text-embedding-v1）：只负责将文本转为向量，需求简单，成本极低

分开配置可以：
1. **节约成本**：Embedding用便宜的模型（如DashScope的），LLM用高质量模型
2. **灵活切换**：可以独立更换任一服务提供商
3. **独立扩缩容**：两类调用的频率和延迟要求不同，独立部署更合理

---

#### Q8: 意图路由是怎么实现的？为什么不训练一个分类模型？

**A:** 使用LLM本身做意图分类，结合对话上下文（是否有已有报告、是否有任务列表）进行判断。理由：
1. **类别少且明确**：只有4种意图（新研究/追问/调整/闲聊），不需要专门的分类模型
2. **依赖上下文理解**：比如"帮我深入分析第三章"需要理解之前的研究内容，LLM天然擅长
3. **灵活性强**：新增意图类型只需要修改prompt，不需要重新训练模型
4. **开发成本低**：4种类别的few-shot分类用LLM做准确率已经足够高

---

#### Q9: 你怎么保证Planner生成的任务是互补的、不重复的？

**A:** 三个层面保障：
1. **Prompt工程**：系统提示词明确要求"生成互补的、非冗余的任务，覆盖课题的不同维度"
2. **注入历史上下文**：将长期记忆中相关研究的已有任务注入到Planner的输入中，避免重复已有研究
3. **评估验证**：Planner Evaluator中有"任务多样性"指标（20分），检查query的唯一性比例

实际效果：评估中Planner平均得分93/100，任务重复率很低。

### 第三类：工程实践

#### Q10: 并行执行时，多个Summarizer的结果是怎么合并的？

**A:** 使用LangGraph的状态注解机制：
```python
class ResearchState(TypedDict):
    task_results: Annotated[list, operator.add]
    sources: Annotated[list, operator.add]
```

`Annotated[list, operator.add]`告诉LangGraph：当多个并行节点都写入这个字段时，自动用`+`操作合并列表。所以每个Summarizer返回`{"task_results": [result1], "sources": [src1]}`，LangGraph会自动合并成完整的列表。这比手动管理并发安全的数据结构要简洁得多。

---

#### Q11: SSE流式推送是怎么实现的？

**A:** FastAPI的StreamingResponse + SSE格式：
```python
async def stream_research(topic):
    async def event_generator():
        yield f"data: {json.dumps({'status': 'planning'})}\n\n"
        # 执行Planner
        yield f"data: {json.dumps({'status': 'searching', 'task': task_title})}\n\n"
        # 执行Summarizer（每个任务）
        yield f"data: {json.dumps({'status': 'reporting'})}\n\n"
        # 执行Reporter
        yield f"data: {json.dumps({'status': 'done', 'report': report})}\n\n"
    return StreamingResponse(event_generator(), media_type="text/event-stream")
```

前端通过`EventSource`接收事件，实时更新UI显示研究进度。

#### Q12: 你的评估体系是怎么设计的？为什么要有这个？

**A:** 三个维度的评估：
- **Planner评估**（100分）：JSON格式(30) + 任务数量(20) + 字段完整性(30) + 任务多样性(20)
- **Summarizer评估**（100分）：内容存在(20) + 内容深度(30) + 来源验证(30) + 内容长度(20)
- **Reporter评估**（100分）：内容存在(15) + 内容长度(15) + 章节完整性(40) + 格式与链接(30)

为什么需要：
1. **量化系统质量**：不是"感觉不错"，而是有客观数据证明系统表现
2. **发现薄弱环节**：比如某个Topic的Summarizer得分低，说明搜索结果质量差
3. **迭代优化依据**：修改Prompt后可以跑评估对比分数变化
4. **面试加分项**：展示了对AI系统质量的工程化思维

#### Q13: 你遇到的最大技术挑战是什么？怎么解决的？

**A:** **并行任务的可靠性问题**。

挑战：5-7个搜索任务并行执行时，经常会遇到：搜索API限流、返回空结果、LLM输出格式错误（不是合法JSON）等，导致部分任务失败，最终报告缺失关键内容。

解决方案：
1. **搜索降级**：三级搜索策略确保至少能获取到信息
2. **重试+替代查询**：每个任务3次机会，失败时生成替代搜索词
3. **质量门控**：检查内容长度和来源数量，不达标的触发重试
4. **兜底生成**：如果3次都失败，让LLM基于自身知识生成回退内容
5. **JSON解析容错**：多层正则提取，解析失败时使用默认任务模板

最终评估中15个课题平均得分94.6/100，证明了这套容错机制的有效性。

#### Q14: 如果让你优化这个项目，你会怎么做？

**A:** 几个方向：
1. **引入Reranking**：搜索结果先用Cross-Encoder重排序，提高输入给LLM的内容质量
2. **层次化研究**：对复杂课题支持多轮Planning，第一轮的摘要反馈给Planner生成更深入的子任务
3. **用户反馈闭环**：让用户对报告打分/修改，将反馈写入长期记忆优化后续研究
4. **成本优化**：对简单子任务用小模型（如GPT-4o-mini），复杂任务才用大模型
5. **缓存层**：对相似查询的搜索结果做缓存，避免重复调用搜索API
6. **异步队列**：将研究任务放入消息队列（如Redis/Celery），支持更大并发

### 第四类：AI应用开发通用问题

#### Q15: 你如何处理LLM输出不稳定（幻觉、格式错误）的问题？

**A:** 多层策略：
1. **Prompt工程**：明确的系统提示词，指定输出格式和约束
2. **结构化输出**：要求JSON格式输出，配合Pydantic验证
3. **工具锚定**：通过ReAct模式让Agent基于搜索结果生成内容，而非纯靠LLM编造
4. **引用追踪**：要求每个论点必须附带来源URL，可以追溯验证
5. **重试机制**：格式错误时重新调用LLM，最多3次
6. **兜底策略**：所有重试失败后使用安全的默认值

#### Q16: 你项目中用了哪些Prompt Engineering技巧？

**A:**
1. **角色定义**：每个Agent有明确的系统提示词定义其角色和职责
2. **输出格式约束**：明确要求JSON格式输出，指定字段名和含义
3. **Few-shot示例**：在关键Prompt中提供输入输出示例
4. **上下文注入**：将记忆中的相关信息动态注入到Prompt中
5. **链式思考引导**：通过"先分析...再...最后..."的结构引导LLM按步骤推理
6. **质量约束**：明确要求"不要编造来源"、"内容必须>200字"等硬约束

#### Q17: ChromaDB在你的项目中扮演什么角色？为什么选它？

**A:** ChromaDB作为长期记忆的向量存储引擎，存储所有历史研究报告。当用户发起研究时，系统用当前课题做语义检索，找到最相关的3篇历史报告，作为上下文注入到Planner的Prompt中。

选择ChromaDB的原因：
1. **轻量嵌入式**：不需要单独部署数据库服务，直接文件存储
2. **LangChain原生集成**：有`VectorStoreRetrieverMemory`开箱即用
3. **足够的能力**：项目数据量不大，ChromaDB的检索性能完全够用
4. **易迁移**：如果后续需要升级到Milvus/Pinepine，LangChain的抽象层让切换成本很低

#### Q18: 你的前端是怎么处理后端返回的Markdown报告的？

**A:** 三步处理流水线：
1. **Marked.js解析**：将Markdown转为HTML

#### Q19: 谈谈你对Agent系统的理解。什么样的任务适合用Agent？

**A:** Agent的核心特征是**自主决策**——不是按照预设流程执行，而是根据观察到的信息动态决定下一步行动。

适合用Agent的场景：
1. **需要多步推理**：如深度研究，需要"搜索→分析→补充搜索→综合"
2. **工具依赖动态选择**：不同情况下需要调用不同的工具
3. **需要自我纠错**：搜索结果不好时换关键词重试
4. **开放式任务**：没有固定的执行路径

不适合的场景：
1. **确定性流程**：如数据ETL，每步都确定，用DAG更好
2. **低延迟要求**：Agent的LLM调用延迟高
3. **成本敏感**：多次LLM调用成本显著

我的项目正好符合Agent的适用场景——研究课题开放、需要多轮搜索决策、需要根据搜索结果调整策略。

#### Q20: 你如何看待LangGraph、CrewAI、AutoGen这些Agent框架？

**A:** 三个框架的核心差异：
- **LangGraph**：基于状态图的编排，开发者显式定义节点和边，对流程有完全控制力。适合需要精确控制Agent协作流程的场景
- **CrewAI**：基于角色的协作模型，定义不同角色的Agent，它们自主决定如何协作。更偏"自组织"，开发者控制力较弱
- **AutoGen**：基于多轮对话的协作，Agent之间通过消息传递沟通。适合模拟团队讨论的场景

我选LangGraph是因为：
1. 研究流程有明确的阶段（规划→搜索→报告），状态图天然匹配
2. 需要并行执行搜索任务，LangGraph的Send机制最直接
3. 需要精确控制状态流转，不希望Agent"自作主张"
