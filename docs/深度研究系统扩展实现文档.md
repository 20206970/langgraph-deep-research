# 深度研究系统扩展实现文档

## 1. 文档说明

本文档将 [AI 应用开发扩展计划](AI应用开发扩展计划.md) 转换为可执行的实现路线，覆盖：

1. P0：结构化数据契约、来源追踪、引用校验和离线回归；
2. P1：计划确认、checkpoint 恢复、LangSmith 可观测性、SSE 事件和成本控制；
3. P2：用户文档和 PDF 检索增强。

实现顺序必须保持为 `P0.1 -> P0.2 -> P0.3 -> P1 -> P2`。后续阶段只能建立在前一阶段的验收结果之上，不能绕过 P0 直接增加新 Agent 或新工具。

本项目的目标是可完整演示、可重复验收的个人项目。本文不定义生产级多租户、分布式任务调度或完全自动事实判定。

## 2. 当前代码与改造边界

| 当前模块 | 当前职责 | 改造后职责 |
| --- | --- | --- |

## 4. P0.1：研究产物、State 与结构化输出

### 4.1 目标

将当前的列表聚合状态升级为有稳定 ID、可序列化、可 checkpoint 的研究产物。并行节点不得再依赖 `task_results` 与 `tasks` 的列表位置对应关系。

### 4.2 模型定义

在 `src/state.py` 增加以下 Pydantic 模型和枚举。模型在 Agent 输入输出边界使用，写入 LangGraph State 时统一通过 `model_dump(mode="json")` 转为字典。

```text
RunStatus: planned | confirmed | running | succeeded | failed | cancelled
TaskStatus: planned | confirmed | running | succeeded | failed | cancelled
ParseStatus: valid | repaired | rejected

ResearchRun:
  schema_version, run_id, thread_id, plan_id, plan_version
  status, topic, model_versions, prompt_versions, created_at, updated_at

TaskItem:
  task_id, title, intent, query, status, query_history

TaskPlan:
  schema_version, plan_id, plan_version, topic, tasks, parse_status

SourceItem:
  source_id, source_type, provider, canonical_url
  title, retrieved_at, content_hash, evidence_excerpt, locator

TaskSourceRef:
  task_id, source_id, query, attempt, associated_at

Claim:
  claim_id, task_id, text, source_ids, evidence_status

TaskResult:
  task_id, status, attempts, query_history, summary
  source_ids, claims, error_code, error_message
  latency_ms, token_usage, parse_status

ReportArtifact:
  report_id, report_version, run_id, markdown, claim_ids, status, created_at
```

规则：

1. 所有 ID 使用 UUID 或由稳定字段生成的 SHA-256 前缀；
2. `task_id` 在同一个 `TaskPlan` 内唯一，重试与查询修订不生成新的任务 ID；
3. `source_id` 基于 `canonical_url + content_hash` 生成。相同 URL 内容变化时产生新的来源快照；任务与来源通过 `TaskSourceRef` 关联；
4. `schema_version` 初始为 `1`，新增或删除持久化字段时递增；
5. `error_message` 只能保存脱敏后的摘要，原始模型输出不能直接写入持久化 State。

### 4.3 LangGraph State

将 `ResearchState` 改为 `TypedDict` 风格的 JSON 容器。State 不保存 Pydantic 对象、LLM 实例或不可序列化回调。

```text
ResearchState:
  run: dict
  plan: dict
  task_results: dict[task_id, dict]
  sources: dict[source_id, dict]
  task_source_refs: dict[task_id, list[source_id]]
  report: dict | None
  session_id: str | None
```

实现两个 reducer：

1. `merge_task_results(left, right)`：以 `task_id` 合并，拒绝同一任务同版本的冲突写入；
2. `merge_sources(left, right)`：以 `source_id` 去重，保留完整度更高的来源记录；
3. `merge_task_source_refs(left, right)`：以 `task_id + source_id` 去重，保留检索查询和尝试次数。

Reporter 必须遍历 `plan.tasks` 的顺序，并按 `task_id` 从 `task_results` 读取结果。失败任务应生成“证据不足或任务失败”段落，不允许用无来源内容补齐。

### 4.4 Planner 与 Summarizer 输出处理

保留现有 ReAct Agent，但把最终回复解析收敛到独立函数：

| 位置 | 新函数 | 行为 |
| --- | --- | --- |
| `src/graph/research.py` | `parse_task_plan` | 提取 JSON，校验为 `TaskPlan` |
| `src/graph/research.py` | `parse_task_result` | 提取摘要、来源和结论，校验为 `TaskResult` |
| `src/validation.py` | `validate_plan` | 校验任务数、空字段、重复查询、状态 |
| `src/validation.py` | `validate_task_result` | 校验来源、结论、任务 ID 和状态 |
| `src/validation.py` | `repair_structured_output` | 最多一次结构修复，不重新执行搜索 |

处理策略：

1. 首次解析成功，标记为 `valid`；
2. 首次解析失败时，仅发送“修复为指定 JSON，不添加事实”的修复请求，最多一次，成功标记为 `repaired`；
3. 修复失败标记为 `rejected`，Planner 返回可读错误并停止执行；Summarizer 返回失败 `TaskResult`，Reporter 保留失败状态；
4. 搜索失败重试与格式修复分开计数：保留当前最多三次搜索尝试，结构修复最多一次；
5. 将模型原始输出的哈希、长度、解析错误码写入运行记录，必要时在本地开发环境保存截断后的脱敏文本。

## 5. P0.2：来源归一化、证据链与引用校验

### 5.1 来源归一化

在 `src/tools/search.py` 保持工具函数返回 JSON 字符串的兼容形式，但在工具层对每条结果计算 `source_id` 并统一返回以下字段：

```text
source_id, provider, source_type, title, url, content, retrieved_at
```

ReAct Agent 会直接从工具消息中看到 `source_id`。`search_summarize_node` 在 Agent 结束后收集本轮 ToolMessage 的来源，创建 `TaskSourceRef`，再校验最终 `TaskResult` 与 `Claim` 引用的 ID 是否属于该任务。

工具层的 `normalize_sources(raw_results)` 负责：

1. 去除 URL fragment 和常见跟踪参数，得到 `canonical_url`；
2. 将正文或搜索摘要裁剪为最大 1,500 字符的 `evidence_excerpt`；
3. 对 `canonical_url + evidence_excerpt` 计算内容哈希与 `source_id`；
4. 保存来源引擎和抓取时间；检索查询、尝试次数和任务归属写入 `TaskSourceRef`；
5. 同一 `source_id` 只保留一次；同 URL 不同内容哈希保留为不同快照；
6. 对没有 URL 的来源保留 provider 标识和内容哈希，但标记为不可访问来源。

不要在 P0.2 中抓取或持久化完整网页正文。评测和引用只使用必要的摘要片段、URL 与定位信息，避免无界存储和版权风险。

### 5.2 Claim 级引用

更新 Summarizer Prompt，要求最终输出：

```json
{
  "summary": "任务摘要",
  "claims": [
    {
      "text": "可验证结论",
      "source_ids": ["src_xxx"],
      "evidence_status": "supported"
    }
  ]
}
```

工具调用返回的来源 JSON 已包含 `source_id`，Summarizer 在最终输出中只能引用本轮工具消息出现的 ID。图层解析器再以 `TaskSourceRef` 校验，拒绝引用当前任务以外的来源 ID。

Reporter 的输入为已排序 `TaskResult`、`SourceItem` 与 `Claim`。每个关键结论后以 Markdown 脚注或链接标记来源；`evidence_status=insufficient` 的结论必须明确展示“证据不足”，不能生成确定性措辞。

### 5.3 引用校验器

在 `src/citations.py` 实现：

| 函数 | 规则 |
| --- | --- |
| `validate_reference_structure` | `source_id` 存在、属于当前任务、无重复 ID |
| `validate_source_accessibility` | 按配置检查 URL 或评测快照可读取 |
| `calculate_citation_coverage` | 有来源的关键结论数 / 关键结论总数 |
| `find_cross_task_references` | 检查结论引用了其他任务的来源 |
| `build_citation_report` | 输出任务级问题和汇总指标 |

“证据支持”不由 URL 状态推断。初始版本只对固定评测集中的关键结论使用人工标注；后续引入 LLM Judge 时，必须先抽样对比人工标签并记录一致性。

验收：

### 6.1 数据集布局

新增以下目录，不覆盖现有临时评测文件：

evaluation_data/

初始 `v1` 从现有 12 个主题中筛选并人工审阅，覆盖技术综述、论文调研、事实问答和对比分析。每条 case 至少包含：

```text

```

来源快照只保存 URL、抓取时间、证据片段、内容哈希和来源引擎。`claim_annotations.jsonl` 保存关键结论与人工证据支持标签。

### 6.2 Runner 改造

将 `src/evaluation/runner.py` 拆分为：

| 模块 | 职责 |
| --- | --- |
| `dataset.py` | 读取、校验和版本化数据集 |
| `fixtures.py` | Fake Search / 快照检索 |
| `metrics.py` | 计算结构、来源、引用、延迟和失败指标 |
| `runner.py` | 协调多轮执行和原始结果落盘 |
| `report.py` | 生成 Markdown 汇总 |

新增 CLI 参数：

```text
--dataset evaluation_data/v1
--runs 3
--offline
--model-label <label>
--prompt-version <version>
--output-dir evaluation_results/<run>
```

`--offline` 时只读取来源快照，不访问 Tavily、DuckDuckGo、ArXiv 或 Semantic Scholar。线上模式可用于探索，但不能与离线基线混为同一组结论。

### 6.3 指标定义

| 指标 | 定义 |
| --- | --- |
| 计划有效率 | 可解析且通过业务规则的 TaskPlan 比例 |
| 任务覆盖率 | 已覆盖预期维度数 / 预期维度总数 |
| 任务重复率 | 语义或查询重复任务数 / 总任务数 |
| 来源存在率 | 含至少一个来源的关键结论数 / 关键结论总数 |
| 引用结构有效率 | 通过 `validate_reference_structure` 的引用数 / 引用总数 |
| 证据支持率 | 与人工标签或已校准 Judge 一致的关键结论数 / 标注结论数 |
| 失败率 | `failed + rejected` 任务数 / 总任务数 |
| 降级率 | 使用搜索降级或无证据结果的任务数 / 总任务数 |
| 延迟 | 每阶段与全流程的中位数、最小值、最大值 |
| 成本 | 可获取时按模型返回 usage 和价格表计算；不可获取时明确标记为缺失 |

同一配置至少执行 3 次，报告中位数、最小值、最大值和失败率，不把单次结果写入简历。

### 6.4 P0.3 验收

- 数据集、来源快照、标注和 Runner 配置均有版本；
- 离线模式可一键执行且不访问外部网络；
- Planner 评测与完整图使用同一 `TaskPlan`；
- 无来源任务仍参与 Reporter 与失败率统计；
- `summary.md` 中的每个汇总数字可回溯到 `results.json`；
- 基线结果存档后，后续 Prompt 或模型变更均生成新目录而不覆盖旧结果。

## 7. P1.1：计划确认、持久化与恢复

### 7.1 持久化选择

个人项目阶段使用 SQLite：

1. LangGraph 使用 SQLite checkpointer 保存图执行快照；
2. 业务产物使用同一 SQLite 数据库的独立表保存，避免把计划版本和报告版本混入 checkpoint 内部表；
3. `thread_id` 固定等于 `run_id`，用于恢复对应的图运行；
4. State 只保存 JSON 兼容数据，并随 `schema_version` 演进。

需要新增 `langgraph-checkpoint-sqlite` 依赖。若未来切换数据库，只替换 repository 与 checkpointer 配置，不改变 API 语义。

### 7.2 数据表与状态机

新增 `src/repository.py`，封装 SQLite 读写；不要在 API handler 中直接拼接 SQL。

```text
plans(plan_id, plan_version, topic, payload_json, status, created_at)
runs(run_id, thread_id, plan_id, plan_version, status, created_at, updated_at)
task_runs(run_id, task_id, attempt, payload_json, status, updated_at)
report_versions(report_id, run_id, version, payload_json, created_at)
event_logs(event_id, run_id, task_id, event_type, payload_json, created_at)
```

状态流转：

```text
计划: planned -> confirmed | cancelled
运行: confirmed -> running -> succeeded | failed | cancelled
任务: confirmed -> running -> succeeded | failed | cancelled
```

修改计划时生成新 `plan_version`，已确认版本不可覆盖。重试只增加 `attempt`，不改变 `task_id`。Reporter 根据当前成功和失败的任务结果生成新的 `report_version`。

### 7.3 API 设计

保留旧接口保证兼容，并新增：

| 接口 | 行为 |
| --- | --- |
| `POST /plans` | 生成并保存 `planned` 状态 TaskPlan，不执行搜索 |
| `GET /plans/{plan_id}/versions/{version}` | 查询计划内容与状态 |
| `PUT /plans/{plan_id}/versions/{version}` | 创建修改后的新计划版本 |
| `POST /plans/{plan_id}/versions/{version}/confirm` | 确认计划 |
| `POST /runs` | 基于已确认计划创建 run，并启动图执行 |
| `POST /runs/{run_id}/resume` | 从最新 checkpoint 恢复 |
| `POST /runs/{run_id}/tasks/{task_id}/retry` | 重试失败任务并生成新报告版本 |
| `GET /runs/{run_id}` | 查询运行、任务和报告版本状态 |

旧 `/plan` 保持只生成计划；旧 `/research` 保持一键路径，但内部以“生成计划 -> 自动确认 -> 创建运行”的兼容流程实现。前端改造后默认使用新计划确认流程。

### 7.4 P1.1 验收

- 未确认计划不能调用搜索工具；
- 计划修改产生递增版本，旧版本仍可查询；
- 进程重启后能通过 `run_id` / `thread_id` 继续执行；
- 单个任务重试不重复成功任务，并生成新的 `report_version`；
- 使用 Fake LLM、Fake Search 覆盖确认、取消、恢复和重试的集成测试。

### 7.5 实现状态

P1.1 已实现：`SQLiteRepository` 将计划版本、运行、任务尝试、报告版本和事件日志保存到同一 SQLite 数据库；研究图可接受已确认计划并使用 `run_id` 作为 LangGraph checkpoint 的 `thread_id`。新增 API 覆盖计划创建、版本修改、确认、取消、运行、恢复、任务重试与查询；旧 `/research` 通过“生成计划 -> 自动确认 -> 创建运行”保持兼容。取消运行会同步标记未完成任务，并拒绝写入迟到的图结果，避免取消状态被覆盖。自动化测试使用临时 SQLite 与 Fake Graph 验证计划门禁、确认计划跳过 Planner、checkpoint 跨实例读取、恢复调用、取消终态、报告版本递增和失败任务定向重试。

## 8. P1.2：LangSmith、SSE 与本地事件

### 8.1 Trace 策略

在 `src/config.py` 增加 `TracingConfig`：

```text
enabled, endpoint, api_key, project, sample_rate
capture_content, retention_days, redact_patterns
```

`.env.example` 只展示变量名，不写入真实密钥：

```text
LANGSMITH_TRACING=false
LANGSMITH_API_KEY=
LANGSMITH_PROJECT=langgraph-deep-research-dev
LANGSMITH_ENDPOINT=
```

规则：

1. 本地开发和离线评测可显式开启 Trace；
2. 部署环境默认禁用内容采集；
3. API Key、认证头、完整用户文档、完整报告和原始搜索正文永不上传；
4. Trace metadata 只记录 `run_id`、`session_id`、`task_id`、节点名、模型名、Prompt 版本、搜索源、重试次数和脱敏状态；
5. LangSmith 不可达时捕获异常、记录本地脱敏日志，但不影响研究流程；
6. Trace 保留时间与删除流程由配置和手工验收记录保证。

LangSmith 负责开发和评测诊断；它不替代 SSE，也不作为业务状态的唯一来源。

### 8.2 本地事件与 SSE

新增 `src/events.py`，定义以下事件：

```text
planning
plan_confirmed
task_started
searching
retrying
task_completed
task_failed
reporting
completed
failed
```

统一事件 envelope：

```json
{
  "event_id": "evt_xxx",
  "run_id": "run_xxx",
  "task_id": "task_xxx",
  "type": "task_completed",
  "timestamp": "ISO-8601",
  "payload": {
    "status": "succeeded",
    "attempt": 1,
    "latency_ms": 1234
  }
}
```

`src/main.py` 的流式接口改为输出标准 SSE：

```text
event: task_completed
id: evt_xxx
data: { ... }
```

每个事件同时写入 `event_logs`。前端先在 `App.vue` 中消费任务状态和错误摘要，报告正文仍通过现有 Markdown 渲染组件展示。

### 8.3 P1.2 验收

- 一次运行的 LangSmith Trace 能展开到图节点、LLM 和工具调用；
- 使用 `run_id`、`task_id`、模型版本可筛选 Trace；
- 关闭 Trace 或模拟 LangSmith 网络错误时，运行可完成且本地事件完整；
- SSE 客户端可按事件类型实时显示任务状态；
- Trace 和事件日志的脱敏测试不包含密钥、认证头或原始私有文档内容。

### 8.4 实现状态

P1.2 已实现：`src/events.py` 提供事件 envelope、脱敏、线程安全发布和标准 SSE 编码；`event_logs` 支持结构化事件追加与查询。研究图已接入计划、任务、搜索重试、报告和终态事件，`/research/stream` 使用持久化一键运行流程输出标准 SSE；LangSmith 通过 `TracingConfig` 可选接入，默认关闭且构造/网络失败自动降级。前端首次研究请求消费 SSE 更新任务状态，后续多轮对话继续使用原有 REST 接口。测试覆盖脱敏、事件落库、Trace 降级、图节点事件和 SSE 终态报告，前端构建通过。

## 9. P1.3：模型路由、缓存与预算

### 9.1 模型角色

在 `src/config.py` 引入按角色配置的模型映射：

```text
router_model
planner_model
summarizer_model
reporter_model
repair_model
judge_model
```

在 `src/llm.py` 提供 `create_llm(role: str, **overrides)`，由角色选择模型、温度和最大 Token。Router、Planner 与格式修复优先轻量模型；Summarizer、Reporter 使用高能力模型。模型名与 Prompt 版本必须写入 `ResearchRun` 和评测结果。

### 9.2 搜索缓存

新增 `src/cache.py`，个人项目阶段使用 SQLite TTL 缓存。缓存键：

```text
normalized_query + provider_config + language + max_results + tool_version
```

缓存 value 必须保存来源快照、`source_id`、创建时间与过期时间。缓存命中时在 `TaskResult`、SSE 事件和 Trace 中标记 `cache_hit=true`。来源配置或工具版本变化必须失效，不能将旧来源伪装为实时检索结果。

### 9.3 预算控制

新增 `RunBudget`：

```text
max_tasks, max_search_attempts, max_format_repairs
max_total_tokens, max_estimated_cost, max_elapsed_seconds
```

预算达到上限时停止后续可选任务并生成 `budget_exceeded` 失败状态；Reporter 仅汇总已经完成的任务，并在报告中标注范围限制。

### 9.4 P1.3 验收

- 相同缓存键的重复请求不重复调用搜索工具；
- 工具版本或来源配置变化后缓存失效；
- 可获得 usage 时统计模型 Token 和估算成本；不可获得时明确标记缺失；
- 预算耗尽不会产生伪成功报告；
- 固定离线评测集能比较至少两套模型路由的质量、延迟和成本。

## 10. P2：用户文档与 PDF RAG

P2 在 P0.2 来源与引用模型稳定后实施。新增模块：

```text
src/documents.py       文件校验、解析与切块
src/knowledge_base.py  索引、检索、删除和版本管理
src/document_store.py  文档元数据与访问范围
```

实现流程：

```text
上传 Markdown / PDF / 网页
  -> 类型、大小、文件名、解析时长校验
  -> 文档 ID 与版本
  -> 分块、页码 / 段落定位、向量化
  -> 按文档范围检索
  -> SourceItem 生成文档来源
  -> Claim 引用文档名与页码
```

约束：

1. 文件使用白名单和大小上限；
2. 解析在超时和异常隔离下运行；
3. 删除文档必须删除关联向量、元数据和缓存；
4. 检索必须接受允许的 `document_ids`，不允许跨范围返回内容；
5. PDF 引用需要保存页码；Markdown 和网页引用保存段落或 URL 定位；
6. 文档删除后运行检索回归测试，确认不再返回已删除内容。

P2 验收后才可以在简历中把该项目称为“用户文档 RAG / 知识库研究应用”。

## 14. 实施协作策略

协作原则是“核心边界直接实现，稳定后的独立模块交给子代理”。子代理只能在输入输出契约、涉及文件范围和验收标准已经冻结后开始工作；主线负责接口设计、集成、回归测试和最终验收。

| 阶段 | 建议方式 | 理由 | 子代理边界或主线责任 |
| --- | --- | --- | --- |
| P0.1 数据契约、State、结构化输出 | 直接实现 | 同时影响 `state.py`、研究图、三个 Agent 和测试基础设施，是全项目的共同输入输出边界。字段或 reducer 不一致会导致后续返工。 | 主线完成全部实现与测试；不委派共享模型和 State 修改。 |
| P0.2 来源归一化与引用校验 | 直接实现 | 与 P0.1 的 `TaskResult`、`SourceItem`、`TaskSourceRef`、工具消息和 Reporter 强耦合。 | 主线统一实现搜索工具返回格式、引用契约与图层校验。 |
| P0.3 离线评测与回归 | 子代理实现 | P0.2 稳定后，数据集、Fixture、指标和报告生成位于 `src/evaluation/`，与主业务图相对隔离。 | 子代理实现数据集加载、离线 Fixture、指标与报告；主线冻结口径、审查样本和验收基线。 |
| P1.1 计划确认、SQLite checkpoint、恢复 | 直接实现 | 涉及状态机、业务表、API 语义、`thread_id`、报告版本与恢复行为，是第二个核心边界。 | 主线负责 repository、checkpoint、API 和集成测试。 |
| P1.2 LangSmith、SSE、本地事件 | 子代理实现 | 事件 envelope 与脱敏规则冻结后，Trace 配置、事件封装、SSE 输出和前端状态展示可以独立推进。 | 主线先定义事件和隐私策略；子代理实现可观测性模块与前端事件消费；主线做端到端验收。 |
| P1.3 模型路由、缓存、预算 | 子代理实现 | 依赖稳定的配置、评测和事件接口，模型工厂、缓存和预算控制可在限定文件内独立实现。 | 子代理不能修改 P0 产物契约；主线审查缓存键、预算失败语义和评测对比结果。 |
| P2 用户文档 / PDF RAG | 直接主导，拆分子任务 | 文件上传、解析、索引、检索、删除、引用和前端共同组成新子系统，整体委派会放大集成和安全风险。 | 主线先完成独立设计；可委派文档解析测试、索引删除回归或前端上传组件等不重叠子任务。 |

### 14.1 子代理启动条件

只有同时满足以下条件，才可将阶段或子任务交给子代理：

1. 对应阶段的前置阶段已经通过验收；
2. 输入输出模型、事件格式、API 或评测口径已经写入本文档；
3. 子任务的修改文件和不允许修改的共享文件已明确；
4. 子任务可以使用 Fake LLM、Fake Search 或离线数据完成测试；
5. 子代理的交付物包含代码、测试和运行说明，而不只是实现描述。

### 14.2 主线集成责任

无论是否委派，主线必须负责：

1. 审查是否修改了 P0 数据契约、状态机或隐私边界；
2. 合并后运行全量单元测试、图集成测试和相关 API 测试；
3. 在 P0.3 固定数据集上检查质量、失败率、延迟和成本是否发生回归；
4. 复核 LangSmith Trace 与本地事件不包含敏感内容；
5. 只在代码、测试、演示和原始指标齐全后更新简历表述。
